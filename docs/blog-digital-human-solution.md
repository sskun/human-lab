# 从零搭建企业可用的数字人系统：human-lab 方案实录

> 一句话：这篇文章讲清楚数字人的实现原理，以及我们如何**零 GPU、纯云端 API** 落地一个"能聊天、能口播"的数字人系统，并把它调到企业可用的效果。所有数据均为实测，非文档转述。

---

## 一、数字人是什么，为什么值得做

数字人是 AI 驱动的虚拟人物形象，具备"听、说、想、演"中的一项或多项能力。按产品形态分两类，工程复杂度差异巨大：

| 形态 | 交互方式 | 典型场景 | 延迟要求 |
|------|---------|---------|---------|
| **实时对话数字人** | 用户说话，数字人听懂并语音回答 | 智能客服、导览、陪伴 | 秒级响应 |
| **内容生成数字人** | 输入一段文案，产出一条口播视频 | 电商带货短视频、企业培训课件、资讯播报 | 分钟级离线任务 |

**前景判断**：内容生成侧已经跑通商业闭环——一条口播视频替代真人出镜，边际成本从"主播+拍摄+剪辑"降到几块钱 API 费用，天然适配短视频平台的海量分发需求。而 2026 年这个时间点做这件事尤其合适：

- 云端大模型 API 覆盖了全部四个核心能力（语音识别、语音合成、对话、视频生成），**一个 API Key、零 GPU** 就能起步；
- 视频生成模型进入"音频驱动"成熟期，一张图 + 一段音频即可生成口型同步的说话视频；
- 按量付费，试错成本可控。

我们的结论是：**先用离线口播场景落地（投入产出比最高），实时对话用纯音频形态先跑通链路**，视频化实时渲染留到业务验证之后。

## 二、整体方案思路

### 2.1 核心认知：数字人 = 4 个 AI 能力 + 1 层工程编排

不要自己训模型。整条链路拆开看，只有四个独立的标准 AI 能力，其余全是普通工程：

```
形态一：实时聊天数字人（纯音频，秒级）
  用户语音 ──ASR──> 文本 ──LLM──> 回复文本 ──TTS──> 回复音频 ──> 播放

形态二：口播数字人（视频，分钟级）
  口播文案 ──TTS──> 音频 ─┐
                          ├──视频生成──> 口播视频 ──> 网页播放
  形象图（一张照片）───────┘
```

这个拆分决定了整个架构：每个能力封装成**独立的"能力层"**，编排层只负责串流程、落库、暴露 HTTP 接口。

### 2.2 工程架构

标准 monorepo，三个包：

```
human-lab/
├─ apps/server/            # NestJS：能力层 + 任务编排 + SQLite 持久化
│  └─ src/
│     ├─ capabilities/     # 纯能力层：tts / asr / llm / lipsync / upload
│     ├─ tasks/            # 口播任务编排（异步流水线 + stage 进度）
│     ├─ chat/             # 聊天编排（会话上下文，每轮 ASR→LLM→TTS）
│     └─ database/         # SQLite（node:sqlite，零外部依赖）
├─ apps/web/               # Vite + React：💬实时聊天 / 🔊口播朗读 双页签
├─ packages/shared/        # 前后端共享的 API 类型契约
├─ lego/                   # 每个能力的"可直接 node 运行"演示块（01-tts ~ 04-lipsync）
└─ assets/avatars/         # 形象资产（AI 生图）
```

几条关键的工程纪律，都是踩坑后固化的：

1. **能力层保持纯粹**：不碰 HTTP、不写数据库，输入进、结果出。好处是 lego CLI 和冒烟测试可以直接引用，新能力 30 分钟就能单独验证。
2. **探测先行**：每接一个新模型 API，先写 probe 脚本实测（可用性/延迟/限制/坑），结论回填设计文档，再动手写业务代码。这个方法论帮我们提前发现了三个官方文档没写清的坑（见 §3.4）。
3. **异步任务 + 轮询**：口播视频生成约 1 分钟，用 `POST /api/speak` 提交 → SQLite 入队 → 后台流水线执行 → 前端轮询 `GET /api/tasks/:id`。单任务双产物（音频 + 视频），失败时音频保留可播。
4. **Provider 兜底链**：能力层接口固定，模型可换。口播视频的兜底链是 `wan3.0-video-prime → wan3.0-video → wan2.2-s2v → 本地 SadTalker`，编排层零改动。

## 三、模块拆解与模型选型

四个能力模型全部走**阿里云百炼专属实例，一个 `DASHSCOPE_API_KEY`**，这是选型的第一原则——收敛供应商、统一计费、同一套鉴权。

| 模块 | 作用 | 项目选型 | 关键实测指标 |
|------|------|---------|-------------|
| TTS 语音合成 | 文本 → 语音 | `qwen-audio-3.0-tts-plus` | WebSocket 流式；系统音色：龙安灵心（女）/ 龙安鲁风（男） |
| ASR 语音识别 | 语音 → 文本 | `qwen-audio-3.1-asr-flash` | 3s 音频 0.3~0.5s 返回；字级时间戳；base64 直传免 OSS |
| LLM 对话 | 文本 → 回复 | `qwen3.8-flash` | OpenAI 兼容接口，SSE 流式，带会话上下文 |
| 口播视频生成 | 形象图 + 音频 → 说话视频 | `wan3.0-video-prime` | 66.8s 生成 10s 视频；时长对齐误差 0.02s |

### 3.1 TTS：文本转语音（qwen-audio-3.0-tts-plus）

走 DashScope `tts_v2` **WebSocket 协议**（比 HTTP 更适合后续做流式播放）。能力层一行调用：`synthesizeSpeech(text, voice) → mp3 Buffer`。TTS 是两条产品线的交汇点——聊天线的"嘴"和口播线的声音来源，因此口播视频的音色就由这里决定。

### 3.2 ASR：语音识别（qwen-audio-3.1-asr-flash）

两个实测结论大幅简化了工程：**音频可以 base64 内联直传**（不需要 OSS 或公网 URL）；**TTS 的 mp3 产物可直接识别**（不需要 ffmpeg 转码）。前端用 Web Audio 采集 → 重采样 16k → WAV → base64 上传，浏览器录音到识别结果的链路一个依赖都不用加。响应自带字级时间戳，为后续做字幕/口型校验留了口子。

### 3.3 LLM：对话大脑（qwen3.8-flash）

标准 OpenAI 兼容 `chat/completions`，SSE 流式。聊天编排层维护会话上下文（`chat_turns` 表落库每轮输入输出），人设通过 system prompt 注入。选 flash 档位是因为聊天场景回复要短、要快，重度推理交给上层产品逻辑。

### 3.4 口播视频生成：音频驱动（wan3.0-video-prime）——系统的核心模块

这是把"声音"变成"会说话的人"的一步。选型逻辑：

- wan3.0 是全能参考生成模型，`reference_image（形象图）+ reference_audio（TTS 音频）` 组合即官方的**音频驱动模式**：模型按音频的语音内容和音色驱动图中人物说话；
- prime 是高速版，端到端更快（实测 67s，远快于官方 1~5 分钟口径）；
- `reference_image` 最多 10 张 → 商品图作为第 2 张参考图即可做"带货口播"；
- 专门的口型模型 wan2.2-s2v 保留为降级兜底（Provider 已预留）。

调用形态是异步任务：上传素材 → 创建任务（`X-DashScope-Async: enable`）→ 轮询 → 下载视频转存。**三个官方文档没写清、实测才踩到的坑**，已固化进代码：

1. 临时上传通道的 getPolicy 接口**必须带 `model` 参数**，且只存在于公网端点；
2. OSS 表单上传的 `key` 是裸对象键，`oss://` 前缀只在最终传给模型时加；
3. 传 `oss://` 临时 URL 时**必须带 `X-DashScope-OssResourceResolve: enable` 请求头**，否则任务 5 秒内失败。

### 3.5 形象资产与编排层

形象 = 一张 AI 生成的照片（规避肖像权），规范对齐模型输入限制：单人正脸、嘴部自然闭合不露齿、纯背景、3:4 构图、≥1024px。编排层是 NestJS 的 tasks/chat 模块 + SQLite，负责状态机（`queued → tts → lipsync → done/failed`）、产物落盘 `output/`、进度暴露。

## 四、定制化：怎么把效果调到"企业可用"

Demo 和企业可用的差距，全在这一节的细节里。

### 4.1 形象定制：基准帧决定成片质量

形象图是视频生成的"基准帧"，它不合格，后面全废。实测有效的提示词要点：

- **正脸平视、头部无偏转、眼神看镜头**——保证生成时不侧脸；
- **微笑但嘴巴闭合、不露齿**——露齿基准帧容易造成张口瑕疵；
- **柔和正面光、纯色摄影棚背景、85mm 人像镜头**——稳定的光线和背景减少形象漂移；
- 构图胸像/半身、3:4，短边 ≥1024px。

生成后自查清单：正脸 ✔ 闭嘴不露齿 ✔ 嘴部无遮挡 ✔ 背景无文字水印 ✔。卡通形象（3D 皮克斯风解说员）同模板可用。

### 4.2 声音与语速：用数据推导限制

实测 TTS 音色 `longanlingxin` 语速为 **5.3 字/秒**，而视频模型的参考音频上限是 15s → 单条口播稿约 80 字，**保守设 60 字上限**（为慢速音色留余量）。这个"字数 ↔ 秒数"标定让前端能在提交前就拦截超长文案，而不是生成失败了才报错。

### 4.3 口播 prompt 模板：精确指令 + 关闭智能改写

`prompt_extend: false` 是关键定制项——我们的口播模板是精确指令，不能让模型自由发挥改写。模板核心结构：

```
图1是数字人主播的形象照。生成竖屏口播视频：图1人物正面面对镜头，
保持形象、服装、发型与背景完全一致，按照音频1中的语音逐句播报，
口型与音频1精确同步，表情自然亲和，伴随轻微手势与头部动作，无字幕。
```

注意**口播文案本身不进 prompt**（内容由音频承载，避免长 prompt 截断），prompt 只约束"怎么演"。商品介绍场景的变体：图2 作为商品图，模板增加"讲到商品时展示图2"。

### 4.4 人设与参数全部配置化

- 聊天人设：`LLM_SYSTEM` 环境变量注入（默认"数字人小泡泡"），要求口语化、回复简短；
- 视频参数：分辨率（480P/720P/1080P）、画幅（9:16/1:1/16:9）、时长策略（`-1` 智能对齐音频）、音色、轮询间隔、超时，全部 `.env` 可调，不动代码。

### 4.5 失败策略与合规

- **口播失败不回滚音频**：TTS 成功的产物保留可播，错误原因入库；
- **产物即时转存**：云端 `video_url` 24h 失效，成功后立刻下载到本地 `output/`；
- **合规三件套**：AI 生图规避肖像权、前端叠加"AI 生成"角标（深度合成显式标识）、审核失败给可读错误不盲目重试。

## 五、最终实现效果

### 5.1 实测数据（probe 脚本可复现）

| 指标 | 实测值 |
|------|--------|
| 口播视频生成耗时 | 受理 → 完成 **66.8s**（10s 成片） |
| 时长对齐 | `duration: -1` 智能时长下，视频 9.98s vs 音频 10s，**误差 0.02s** |
| 成片规格 | 9:16 竖屏、480P、30fps、含原声音轨（音色 = TTS 原声） |
| 口型与形象 | 口型全程清晰开合、同步；形象/服装/背景与形象图**零漂移**；自然眨眼与手势 |
| 聊天链路 | 免按键连续对话（VAD 自动断句），每轮 ASR→LLM→TTS，上下文多轮保持 |
| 成本 | 480P 约 ¥0.45/秒，一条 15s 口播 ≈ **¥6.75**；ASR/TTS/LLM 按量，聊天天级调试成本可忽略 |

### 5.2 使用体验

网页两个页签：**💬 实时聊天**——对着麦克风说话，VAD 自动断句，数字人带着上下文语音回答；**🔊 口播朗读**——输入 ≤60 字文案，勾选"生成口播视频"，看着阶段提示从"合成中"走到"口播视频生成中，约 1 分钟"，然后竖屏视频里数字人对着镜头把文案讲完。

### 5.3 企业落地的建议路径

1. **先跑离线口播**：投入产出比最高，文案试听（纯音频，成本≈0）满意后再生成视频；
2. **聊天场景先纯音频**：实时视频渲染的 GPU 成本在业务验证前不值得投入；
3. **演进路线已预留**：长口播 → 切段生成 + ffmpeg 拼接；专属声音 → 声音克隆；实时视频化 → MuseTalk / LiveTalking 本地推理路线；多形象/多商品模板 → 形象资产目录已按多形象设计。

## 六、未来：门槛消失之后，差距在哪里

先给判断：**门槛消失的是"能不能生成"，门槛转移到了"生成得对不对、稳不稳、便宜不便宜、懂不懂业务"**。调通视频生成 API、接上 TTS、做个能播放的网页——这些半年后就是常识，不构成差距。真正拉开差距的是五件事，按含金量排序：

### 6.1 可控性：从"能说话"到"能表演"（当下最实的差距）

现在模型给你的是"一个会把这段音频念出来的人"，企业要的是"一个主播"：

- **语义-情绪-动作对齐**：文案讲到"惊喜价"时眼神发亮、手势打开——目前只能给"轻微手势"这种模糊指令。把文案结构（强调点、停顿、情绪曲线）翻译成精确的表演指令，本质是把"导演能力"工程化。
- **长视频**：15s 音频上限逼着所有玩家做"切段生成 + 拼接"，接缝处的形象漂移和语气不连贯极难处理。3 分钟口播零破绽，本身就是护城河。
- **跨视频形象一致性**：同一个人不换脸、不变装、撑得起多镜头叙事——全行业尚未真正解决，谁先解决谁拿走品牌客户。

### 6.2 内容工程：模型不值钱，转化率值钱

同样的模型，不同的口播稿，带货转化率差一个数量级。差距在两处：

- **文案侧的数据飞轮**：哪句开头留人、什么节奏促单——这些数据只有跑过量的玩家有。API 人人能调，A/B 测试基础设施和效果数据回流别人没有。
- **自动质检（QC）**：量大之后不可能人眼看片。自动检测口型同步分、形象漂移、音频瑕疵，不合格自动重生成——这是 demo 和生产线的分界线。本项目的任务落库设计（每次生成可追溯、可对账），正是这条路的地基。

### 6.3 实时交互：真正的硬骨头，也是真壁垒

离线生成是分钟级任务，实时对话要亚秒级响应 + 全双工 + 可打断 + 表情随情绪变化。这需要流式 ASR + 流式 LLM + 流式 TTS + 实时渲染（MuseTalk / LiveTalking 路线，需要 GPU）串成一条不断流的管线，还要处理对话的自然感——抢话、停顿、backchannel（"嗯"一声的回应）。**这套实时工程目前完全没有被 API 商品化**，谁先做出来谁独占客服、陪伴这类高粘性场景。

### 6.4 成本工程：规模化后的生死线

¥6.75/条是试错价，一天一万条就是每天六万七。差距在模型路由（简单文案走便宜档）、首帧/素材复用、失败重试策略、云端 API 与自有 GPU 的盈亏平衡测算与混合调度、排队限流与多实例路由。

### 6.5 垂直纵深与合规：B 端的门票

- **领域大脑**：企业买的不是脸，是"懂我家业务的脸"——RAG 接知识库、人设稳定、幻觉可控。脸是云厂商的，大脑是你调的。
- **合规即卖点**：深度合成标识、声音克隆授权链、私有化部署——大企业采购时，"合规的那个选项"经常直接赢。

### 6.6 最短路径建议

| 优先级 | 做什么 | 理由 |
|---|---|---|
| 现在 | 自动 QC + 文案 A/B | 三个月内就能用效果数据拉开差距，投入小 |
| 现在 | 实时渲染小规模预研 | 决定两年后是否还在牌桌上，宜早埋人 |
| 放量后 | 长视频拼接、成本路由 | 规模化客户的入场券 |

## 写在最后

这套系统最重要的经验不是某个模型参数，而是方法论：**能力拆解到最细 → 探测先行实测每个 API → 能力层纯净可独立验证 → 编排层只做胶水 → 兜底链保命**。技术门槛的消失不是坏消息——它意味着竞争回到了更本质的地方：对业务的理解、对效果数据的经营、对可靠性的偏执。而这些，恰恰是从这样一个 200 行能力层 + 一张形象图开始的。
